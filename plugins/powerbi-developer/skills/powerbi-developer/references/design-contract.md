# Design contract (`Design Brief:` YAML)

The design contract is the single artefact that survives from planning into the build. It is the
`Design Brief:` YAML block inside `_brief/report-spec.md` (or a standalone `.yaml`/`.json`).
`scripts/compile_brief_to_batch.py` turns it into `pbir` operations; `pbi-spec-verifier` diffs the
built report against it; `pbi-visual-reviewer` reads it beside the screenshots.

The shape is Microsoft's `powerbi-report-design` brief kept verbatim (so a brief produced by their
skills compiles unchanged), plus plugin extensions prefixed `pbir_`. Adapted from
microsoft/skills-for-fabric (MIT); see THIRD_PARTY_NOTICES.md in the repo root. Read the fixture
`templates/design-brief.example.yaml` once; it is a complete two-page contract that passes every check.

## 1. Top level

| Key | Req | Meaning |
|---|---|---|
| `generated_by` | yes | `powerbi-developer` or `powerbi-report-design` - the marker the compiler and verifier look for |
| `contract_version` | yes | `1` |
| `mode` | yes | `greenfield` (pages are created) or `brownfield` (pages exist; `--pages-mode existing`) |
| `design_identity.tone` / `.signature` | yes | from `reports:pbi-report-design` (tone x signature) |
| `archetype` | no | report-level default archetype |
| `color_map[]` | no | `{role, hex, use}`; roles `primary, neutral, good, bad, accent, series:<name>` |
| `theme.pbir_template` | no | a `pbir theme apply-template` name, or null |
| `theme.data_colors[]` | no | hex list -> `theme_set_colors` |
| `filters[]` | no | `{scope: report|page, page?, table, field, type: Categorical|Advanced|RelativeDate|TopN, values?[]}` -> `pbir add filter` |
| `interaction_pattern`, `accessibility` | no | prose carried into the spec and the reviewer prompt |
| `pages[]` | yes | see below |

## 2. Page

| Key | Req | Meaning |
|---|---|---|
| `name` | yes | page display name (folder name is generated by pbir) |
| `role`, `archetype`, `layout_variant`, `variant_rationale`, `layout_summary` | no | design rationale (reviewer reads them) |
| `page_background` | no | hex -> `pbir pages background --color` |
| `pbir_page` | no | `{width, height, display_option}`; default 1280x720 FitToPage; FHD is `1920x1080` |
| `layout_contract` | yes | `canvas`, `grid`, `placements`, `space_audit` |

### `layout_contract.canvas`

`{ width, height, margin, gutter, snap }` in pixels. Recommended FHD: `1920, 1080, 32, 24, 8`;
HD: `1280, 720, 24, 16, 8`. `width/height` must equal `pbir_page` when both are given.

### `layout_contract.grid`

`columns`, `rows` (12 x 12 recommended) and `regions: { name: [c1, r1, c2, r2] }` with 1-based,
**end-exclusive** coordinates: a region spans columns `c1 .. c2-1` and rows `r1 .. r2-1`, so
`[1,1,13,2]` is the full-width top row and `1 <= c1 < c2 <= columns+1`.

### `layout_contract.placements[]`

| Key | Req | Meaning |
|---|---|---|
| `id` | yes | unique per page; becomes the visual's internal `name` when pbir allows it, and the verifier's match key |
| `region` | yes | a region name |
| `kind` | yes | see the kind table; a raw pbir visual type (`clusteredColumnChart`) is also accepted |
| `slot` / `of` | no | subdivide the region into `of` equal slots along its longer axis, separated by one gutter; this placement takes slot `slot` (1-based) |
| `text` | title/textbox | text content |
| `title` | no | visual title; default: none for cards/slicers, the placement id for others is **not** used |
| `field_bindings` | data visuals | string `"Table[Field]"`, list of strings (assigned to the kind's default roles in order; single-role kinds take all), or `{Role: "Table[Field]" \| [..]}` |
| `slicer_type` | slicer | `dropdown`, `list`, `tile`, `between` -> `pbir_format` presets |
| `sort_policy` | no | `{field: "Table[Field]", direction: Ascending\|Descending}` -> `pbir visuals sort` |
| `color_strategy` | no | `primary`, `neutral`, `diverging`, `series` - applied only where `pbir schema describe` confirms the property |
| `purpose`, `insight_basis` | no | rationale for the reviewer |
| `pbir_visual_type` | no | override the kind -> type mapping |
| `pbir_format` | no | dict of `object.property: value` passed straight to `create_visual.format` (validated by pbir) |

### `layout_contract.space_audit`

`{ unplaced_regions: [], empty_cell_pct: <int> }`. Must be present; `unplaced_regions` must be empty;
`empty_cell_pct` <= 15 (<= 20 for `analytical` pages).

## 3. Pixel rules (what the compiler does)

```
usableW = width - 2*margin                       usableH = height - 2*margin
cellW   = (usableW - (columns-1)*gutter) / columns
cellH   = (usableH - (rows-1)*gutter) / rows
x1 = margin + (c1-1)*(cellW+gutter)              x2 = margin + (c2-1)*(cellW+gutter) - gutter
y1 = margin + (r1-1)*(cellH+gutter)              y2 = margin + (r2-1)*(cellH+gutter) - gutter
x  = round_to_snap(x1)   width  = floor_to_snap(x2 - x1)     (same for y / height)
```

`slot/of`: split the longer axis into `of` equal parts, each `(len - (of-1)*gutter)/of` wide, then
apply the same rounding.

Worked example, 1920x1080 / margin 32 / gutter 24 / snap 8 / 12 columns:
`cellW = (1856 - 264)/12 = 132.67`, `cellW+gutter = 156.67`.

| Region | x | y | width | height |
|---|---|---|---|---|
| header `[1,1,9,2]` | 32 | 32 | 1224 | 56 |
| filters `[9,1,13,2]` | 1288 | 32 | 600 | 56 |

Overlap check: two boxes overlap when they intersect by more than `gutter - snap` pixels on both
axes; ids starting `bg_`, `spacer_`, `divider_` are exempt. Every box must lie inside
`[margin, width-margin] x [margin, height-margin]`.

Role names are the ones `pbir add visual --list` prints (case matters in bindings).

| `card` | `cardVisual` | `Data` |
| `card_classic` | `card` | `Values` |

| `list_slicer` | `listSlicer` | `Values` |
| `table` | `tableEx` | `Values` (all fields) |

| `clustered_bar` | `clusteredBarChart` | `Category`, `Y`, `Series` |

| `clustered_column` | `clusteredColumnChart` | `Category`, `Y`, `Series` |
| `line` | `lineChart` | `Category`, `Y`, `Y2` |
| `area` | `areaChart` | `Category`, `Y` |
| `combo` | `lineClusteredColumnComboChart` | `Category`, `Y`, `Y2` |
| `donut` | `donutChart` | `Category`, `Y` |
| `pie` | `pieChart` | `Category`, `Y` |
| `scatter` | `scatterChart` | `X`, `Y`, `Category`, `Size` |
| `waterfall` | `waterfallChart` | `Category`, `Y`, `Breakdown` |
| `funnel` | `funnel` | `Category`, `Y` |
| `treemap` | `treemap` | `Group`, `Values` |
| `gauge` | `gauge` | `Y`, `TargetValue`, `MinValue`, `MaxValue` |
| `ribbon` | `ribbonChart` | `Category`, `Y`, `Series` |
| `map` | `azureMap` | `Category`, `Size` |
| `filled_map` | `filledMap` | `Category` |

| `image`, `shape`, `button` | `image`, `shape`, `actionButton` | - |

Field syntax: `Table[Field]` (contract) becomes `Table.Field` (pbir). **A table whose name starts
with `.` cannot be bound by pbir** (it splits at the first dot and writes an empty Entity): the
compiler aborts and lists the offending fields; bind those in Desktop or rename the table
(field-parameter literals make the rename risky - see `gotchas.md`).

## 5. Acceptance checklist (compiler errors unless marked W)

1. `generated_by`, `contract_version`, non-empty `pages[]`.
2. Every page has `name`, `layout_contract.canvas/grid/placements/space_audit`.
3. Region coordinates in range; every placement's `region` exists; `slot <= of`.
4. Exactly one `title` kind placement per page (W if missing).
5. Slicers only in regions named `filters`, `rail`, `slicer_rail`, `header` (W otherwise).
6. No data visual placed in a region that also holds a slicer (W).
7. No bare-card hero: a page whose only data visuals are cards (W).
8. `space_audit.unplaced_regions == []`, `empty_cell_pct` within limit (W).
9. No ellipsis (`...` / `...`) in titles/text (W).
10. No overlapping boxes; boxes inside the margins.
11. No `.`-prefixed table in any binding (abort).
12. With `--model-inventory`: every `Table[Field]` exists (W; error with `--strict`).

`--strict` promotes every W to an error.

## 6. Minimal-brief escape hatch

For a single-visual brownfield ask ("add a card for X on Overview") the full contract is overkill.
Write a 3-line minimal brief in `_brief/notes.md` (what, where, binding), get a one-line confirmation,
and use `pbir add visual` directly. The Stop gate still requires validate -> screenshot -> review.
