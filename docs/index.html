Power BI Developer Harness

An agent that plans a report, locks a design contract, waits for your approval, builds it with pbir, then proves the result in Power BI Desktop before it is allowed to say it is done. This page is what it is, how to start it, and which of your tasks belong in it.

01

What it is

Three things existed separately before this. Microsoft's agentic Power BI guidance has the strongest process: define, inspect, spec, approve, build, validate, publish, with an independent screenshot review. The data-goblin marketplace plugins have the strongest tooling: pbir can author almost anything in a PBIR report from the command line. Production PBIP work supplied the scar tissue: a file of rules bought with broken models and lost measures.

This plugin joins them. It routes to the skills and CLIs already on the machine rather than duplicating them, it turns the design brief into a machine-checkable contract, and it uses hooks so the verify loop is enforced rather than merely documented. The agent cannot quietly skip validation, cannot reload a canvas over your unsaved work, and cannot end a turn claiming a change works when nothing rendered it.

The one-sentence version

Describe the Power BI work you want; the plugin plans it, asks once for approval, builds it with pbir, validates it, screenshots it in Desktop, has a second agent review the pixels, and tells you what it could not verify.

Prerequisites

The required tier is what the plugin cannot work without. Everything in the optional tier degrades silently: the skill drops to the next tool in its cascade and says so, rather than failing.

Claude Code 2.1.259+, pwsh 7, uv, git Required winget install astral-sh.uv Windows only. Every hook runs pwsh.
pbir CLI Required uv tool install pbir-cli 0.9.31 tested. The only writer of report JSON.

Power BI Desktop Required Preview feature: Enable external tool access to Power BI Desktop through secure local APIs Without it there is no bridge, so no reload and no screenshots. Restart Desktop after enabling.
Tabular Editor te Optional /powerbi-developer:setup -Install First tier for model writes. Early preview with an expiry date; the banner warns from 10 days out.
Node 20+ and three npm packages Optional /powerbi-developer:setup -Install powerbi-desktop 0.1.2, powerbi-report-author 0.1.4, powerbi-modeling-mcp 0.5.0-beta.13. Managed devices may remove Node; everything falls back to pbir.
Windows PowerShell 5.1 + ADOMD Optional Ships with Windows Needed for the TOM tier. pwsh cannot load TOM at all.
jq Optional /powerbi-developer:setup -WithJq Installing it activates the pbip and pbi-desktop plugins' own bash hooks, which are no-ops without it.
03

Install

Two marketplaces and one install. The six data-goblin plugins it routes to come with it as dependencies. 

# 1. add both marketplaces and install (or run scripts\bootstrap.ps1 from a clone)
claude plugin marketplace add https://github.com/data-goblin/power-bi-agentic-development.git
claude plugin marketplace add https://github.com/willymss/powerbi-developer-harness.git
claude plugin install powerbi-developer@powerbi-developer-harness

# 2. /plugin -> Marketplaces -> enable auto-update for both (off by default for third-party ones)

# 3. restart Claude Code, then install the toolchain (asks before each install)
/powerbi-developer:setup -Install

# 4. confirm it loaded
claude plugin details powerbi-developer@powerbi-developer-harness

In the session itself, /hooks should list five events, /mcp should show powerbi-modeling-mcp connected or a clear Node-missing failure, and /agents should list the three agents. Then give the working folder its harness: 

# permissions, project CLAUDE.md and .gitignore for a Power BI working folder
$H = Get-ChildItem "$env:USERPROFILE\.claude\plugins\cache\powerbi-developer-harness\powerbi-developer" -Directory |
      Sort-Object LastWriteTime | Select-Object -Last 1 | ForEach-Object { Join-Path $_.FullName 'harness-template' }
Copy-Item "$H\settings.json" ".\.claude\settings.json"
Copy-Item "$H\CLAUDE.md"     ".\CLAUDE.md"
Copy-Item "$H\.gitignore"    ".\.gitignore"

Where projects live

PBIP projects go under %PBI_PROJECTS_ROOT%\<name> (default C:\dev\pbi), never OneDrive. Microsoft does not support PBIP on a synced folder, and OneDrive re-applies a ReadOnly attribute to every directory within minutes, which breaks pbir rm, cp and restore mid-operation.

Working on the plugin itself

Clone the repo outside OneDrive and junction ~\.claude\skills\powerbi-developer to its plugins\powerbi-developer; it then loads live as powerbi-developer@skills-dir. On that machine do not also install the marketplace copy, or every hook runs twice. Run scripts\validate.ps1 before pushing.

04

What was built

About forty files. The skill is the operating manual, the agents do the work that should not pollute the main conversation, the hooks are the part you cannot argue with, and the scripts are what both of them call.

ComponentNameWhat it is for
Skillpowerbi-developer The router and operating manual: mode selection, the 11-phase pipeline, brownfield routing table, tool cascade, approval gate, guardrails. Six reference files load only when needed.
Skillsetup Installs, updates or checks the toolchain and prints a status table. User-invoked only, so the model never runs installs on its own.
Agentpowerbi-developer Executes an already approved spec end to end: compile, model changes, batch run, validate, verify loop, dispatch reviewers. Refuses if approval is not cited.
Agentpbi-visual-reviewer Reads the rendered PNGs and the contract, returns findings as issue / location / severity / fix. Read-only, and deliberately not the agent that built the thing.
Agentpbi-spec-verifier Diffs the built report against the approved layout: missing, extra, wrong type, drifted, mis-bound. Every finding carries the pbir command that fixes it.
Hooks8 scripts, 5 events Session banner, hand-edit guard, command guard, encoding guard, evidence ledger, stop gate. See section 08.
Scriptcompile_brief_to_batch.py Turns the design contract into pixel geometry, a pbir batch spec, and three PowerShell build scripts. Aborts on bindings pbir cannot express.
ScriptInvoke-VerifyLoop.ps1 Validate, check Desktop state, reload only if saved, screenshot every page, write a manifest. Distinct exit code per failure mode.
Scriptverify_spec.py Reads the built PBIR JSON and diffs it against the contract. No model connection needed.
Scriptbuild_model_inventory.py Parses a TMDL folder into tables, columns and measures offline, and flags dot-prefixed tables.
ScriptGet-PbiDesktopState.ps1 Normalised Desktop state from pbir, or the raw named pipe, or a test fixture.
ScriptTest-Utf8NoBom.ps1, Get-PbiToolStatus.ps1, Install-PbiTools.ps1 Encoding audit and fix, parallel toolchain probe, installer.
MCPpowerbi-modeling-mcp Microsoft's modeling server, pinned, launched by npx. Fails soft when Node is gone.
Templatesreport-spec.template.md, design-brief.example.yaml The spec skeleton, and a complete two-page contract that doubles as the compiler's test fixture.
05

How to invoke it

Five entry points, in the order you will actually reach for them.

1. Just describe the work

The skill's description matches Power BI phrasing, so it fires on its own. This is the normal path.

Add a YoY variance measure to fact_sales and show it as a card
on the Overview page of C:\dev\pbi\Sales\Sales.Report, then make sure it renders.

2. Name the mode explicitly

When you want a specific stage rather than the whole pipeline.

/powerbi-developer [plan|build|verify|review|publish] [report path]

# examples
/powerbi-developer plan
/powerbi-developer verify "C:\dev\pbi\Sales\Sales.Report"
/powerbi-developer review "C:\dev\pbi\Sales\Sales.Report"

3. Toolchain setup

User-invoked only. Defaults to -Check, which changes nothing.

/powerbi-developer:setup                  # status table only
/powerbi-developer:setup -Install         # first run on a new machine
/powerbi-developer:setup -Update          # refresh pbir, te, the npm CLIs
/powerbi-developer:setup -RepairNode      # after Node was removed

4. Dispatch an agent

The main conversation plans and approves; the agent builds. Useful for anything longer than a handful of commands, because the build noise stays out of your context. 

Use the powerbi-developer agent to build the approved spec at
C:\dev\pbi\Sales\_brief\report-spec.md against Sales.Report, Desktop PID 1234.
I approved it today.

5. Run a script yourself

Every script works standalone, outside any agent.

# the installed copy (a dev clone: <clone>\plugins\powerbi-developer\skills\powerbi-developer\scripts)
$P = Get-ChildItem "$env:USERPROFILE\.claude\plugins\cache\powerbi-developer-harness\powerbi-developer" -Directory |
      Sort-Object LastWriteTime | Select-Object -Last 1
$S = Join-Path $P.FullName 'skills\powerbi-developer\scripts'

# validate + reload + screenshot + manifest
pwsh -NoProfile -File "$S\Invoke-VerifyLoop.ps1" -Report "C:\dev\pbi\Sales\Sales.Report" -DesktopPid 1234

# which tools are present, and what is missing
pwsh -NoProfile -File "$S\Get-PbiToolStatus.ps1"

# is anything in this project carrying a BOM or LF endings?
pwsh -NoProfile -File "$S\Test-Utf8NoBom.ps1" -Path "C:\dev\pbi\Sales" -Recurse -Fix

# contract to build artefacts; then diff the built report against it
uv run "$S\compile_brief_to_batch.py" --spec _brief\report-spec.md --report "C:\dev\pbi\Sales\Sales.Report" --json
uv run "$S\verify_spec.py" --layout _brief\build.layout.json --report "C:\dev\pbi\Sales\Sales.Report" --json

07

The pipeline

Twelve phases, and they really are a sequence: each one consumes the artefact the previous one left. Brownfield work enters at phase 7.

  1. 00

    Tool health

    The session-start hook probes the toolchain and Desktop, and prints a banner naming every running instance and its unsaved flag.

    → banner, tool-status.json
  2. 01

    Define

    At most five rounds, one question each, and it never re-asks something your prompt already answered.

    → _brief\notes.md
  3. 02

    Inspect the model

    Tables, columns and measures are read before anything is designed, so the contract binds fields that exist.

    → _brief\model-inventory.json
  4. 03

    Design

    Tone and signature, a per-page archetype, and a mechanical layout contract on a 12×12 grid.

    → Design Brief YAML
  5. 04

    Spec and approval gate

    One question: Approve this report spec so I can start building? Approve, or revise audience, scope or design. No pbir mutation happens before you answer.

    → _brief\report-spec.md, marked APPROVED
  6. 05

    Compile

    The contract becomes pixel geometry and a batch spec. Contract errors are reported as numbered problems with the contract, never patched in the output.

    → build.layout.json, build.batch.json, build.run.ps1
  7. 06

    Build

    Backup first, model objects through the cascade, then the digest-gated batch. The run script refuses to proceed if any create step resolves zero targets.

    → the built report
  8. 07

    Validate

    Structure, schema, fields, quality and best practices, with a second opinion from the Microsoft authoring CLI. Known false positives are counted separately rather than hidden.

    → _verify\<ts>\validate.json
  9. 08

    Verify the render

    Reload the canvas only if Desktop is saved, capture every page, then hand the images to a reviewer that did not build them.

    → manifest.json, pages\*.png, findings
  10. 09

    Design gate

    The design quality gate runs against both the JSON and the screenshots.

    → findings, no criticals
  11. 10

    Publish

    Optional, gated, and never automatic.

    → workspace URL
  12. 11

    Record

    Anything newly learned goes into the project's own rules file, so the next session starts with it.

    → .claude\rules\*.md
08

The harness

Guarded mode. These run whether or not the skill is loaded, which is the point: they are what makes the process real rather than aspirational.

WhenVerdictWhat it catches
Session startBanner Toolchain versions, every Desktop instance with its unsaved flag and page count, OneDrive and pending-changes warnings, the active pbir profile, and six standing rules.
Before an edit to report.json, mobileState.json, a diagram layout, or anything under .pbi\ Deny Undocumented schemas that Desktop rejects or overwrites. The reason names the pbir command to use instead.
Before any other PBIR, TMDL or theme editAsk Hand-editing report JSON at all; TMDL outside the cascade; theme files that Desktop caches by filename.
Before a canvas reload while Desktop has unsaved changesDeny The single most expensive mistake available: a refresh forces a save, rewrites the whole definition on disk, and can discard either side's work. The reason points at Desktop's own external-changes prompt as the safe direction.
Before a model re-apply, or a reload with several instances open and no PIDAsk Re-applying TMDL when in-memory edits may be pending, or reloading whichever instance happens to be first.
Before publish, rm, restore, copying a visual, clearing formatting, --rawdog, auto-fix with save, field replace, te --save, SaveChanges, destructive git Ask Each prompt carries the specific reason, not a generic warning: copying a visual assigns a new internal name and silently breaks every bookmark that drives it; a failed restore has deleted an unrelated page's visuals before.
After any write to a PBIP fileBlocks A UTF-8 BOM stops the entire project from opening and pbir validate does not catch it. The hook strips it, normalises line endings, and tells the agent what it did.
ThroughoutLedger Every mutation, validation, screenshot, review and model call is recorded per session.
When the agent tries to finishBlocks The stop gate reads that ledger. Mutations with no validation, renders never captured, screenshots never reviewed: it blocks once and names the exact command to run.

Turning it off

The whole harness: set POWERBI_DEVELOPER_HOOKS=off. Individually: nine booleans in $CLAUDE_PLUGIN_DATA\config.json (fallback %LOCALAPPDATA%\powerbi-developer\config.json) — hand_edit_gate, encoding_guard, refresh_guard, hazard_gate, ledger, stop_gate, ask_on_model_reload, require_screenshot, require_review. For testing the guards without Power BI Desktop running, PBI_DEV_FAKE_DESKTOP_STATE takes a JSON fixture.

The artefacts it leaves

Two folders beside the .pbip. Everything is inspectable, and the chain is why a later session can pick up where an earlier one stopped.

FileWritten byContents
_brief\notes.mdPhase 1Answers to the discovery questions.
_brief\model-inventory.jsonPhase 2Tables, columns, measures, and any dot-prefixed table names.
_brief\report-spec.mdPhase 4The spec and the design contract. Locked once approved.

Gotchas worth knowing

These are in references\gotchas.md with detection and fix for each. The first two were found while building this and are not documented anywhere else.

SymptomCauseWhat to do
A batch run reports every step ok and changes nothing pbir batch resolves root only relative to the working directory. An absolute root matches zero targets, silently. Relative root, working directory set to the project folder. The generated run script does this and refuses to continue when a create step resolves nothing.
pbir open launches a different file It resolves through the active pbir profile, not the path you gave it. powerbi-desktop open <.pbip> or Start-Process. Desktop also refuses a second file with the same name, so rename sandbox copies.
A measure binds but the visual never renders A table name starting with a dot: pbir splits at the first dot and writes an empty entity. Bind it in Desktop, or rename the table. The compiler aborts and lists the fields rather than producing a broken report.
Validation reports schema errors on a report nobody touched pbir's bundled schemas lag Desktop's, so newer visual containers fail against an older fallback. The verify loop counts these separately and subtracts them. Use --allow-download-schemas for an authoritative pass.
A theme change does not appear after a reload Desktop caches themes by filename. Rename the theme, or close and reopen Desktop before judging it.
Work disappears after applying changes Both stores were dirty in opposite directions: in-memory model edits and on-disk edits, resolved one way. Never end a turn with TOM and TMDL disagreeing. Write the same change to disk in the same turn.
Could not load type ... CallContext TOM assemblies are .NET Framework and pwsh cannot load them. Run TOM scripts under powershell.exe 5.1. The tool cascade does this automatically.
Two variables corrupt each other in a script PowerShell variable names are case-insensitive, so $new and $NEW are one variable. Never name a loop variable a case-variant of a constant. This has cost real measures more than once.
11

What is proven, and what is not

Tested in September 2026 against a git-baselined sandbox copy of a real report, never against the live project.

Verified

  • ✓Manifests pass claude plugin validate (marketplace and plugin); measured cost is ~812 tokens always-on, ~4.4k when the skill fires.
  • ✓Every hook path unit-tested with piped payloads: ask, deny, BOM strip, invalid JSON, the stop gate's block sequence, and the kill switch.
  • ✓Greenfield build end to end on the sandbox: a page, three visuals with contract-assigned names, a sort and a page filter, and a clean spec diff.
  • ✓Validation triage: 14 degraded-schema errors on the untouched report correctly classified as false positives, leaving zero real errors.
  • ✓Refusals: the loop stops cleanly when Desktop has unsaved changes, and when no instance has the project open.
  • ✓Raw-pipe fallback against a live Desktop: same PID, unsaved flag, file and page count as pbir desktop status.

Not yet exercised

  • ○A live reload plus screenshot round trip. Desktop refuses a second file with the same name, so rename the sandbox copy before running this.
  • ○The eval suite. Three cases are written; claude plugin eval is early access and they need a local fixture.
  • ○The modeling MCP tool surface. The server is pinned and primed but no tool has been called.
  • ○te writes. Reads and validation only so far.
